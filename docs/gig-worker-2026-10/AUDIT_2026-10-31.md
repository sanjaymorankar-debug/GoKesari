# Gig worker (delivery partner) flow — audit, 31 Oct 2026

Phase 1 of the gig worker brief. What the code on `staging` (eaccdaca) already did
for each of the 11 features, and what this change adds. "Rider" and "delivery
partner" are the same thing in the code (`delivery_partners`).

| # | Feature | Already there | Missing (built here) |
|---|---|---|---|
| 1 | Registration with personal details | `POST /api/delivery-partner` → `registerDeliveryPartner` (delivery-partners.ts): name, mobile, optional email and DOB, vehicle type and optional number, PAN/ID/bank (encrypted, SEC-02); form `delivery-partner-register-form.tsx`; one profile per account | Gender, address, emergency contact; email, DOB (18+), vehicle number required; duplicate-mobile check across partners; emergency mobile ≠ own mobile |
| 2 | PAN and Aadhaar authorisation | KYC adapters for sellers (`src/server/kyc`: mock, Gridlines, Sandbox.co.in) — PAN lookup only; consent wording pattern (`lib/kyc/consent.ts`); PAN encryption + blind index (`lib/pan-crypto.ts`). Riders: Aadhaar typed as a free-text "government ID" and stored **encrypted in full** | Rider KYC step: recorded consent, PAN check with the provider (encrypted, masked), Aadhaar OTP check (provider OTP; mock + Sandbox.co.in adapters), Aadhaar kept **masked + tokenised only** (DB check enforces no stored number), Verified / Pending / Failed per document, admin manual decision; full Aadhaar no longer accepted in the free-text ID field |
| 3 | Police verification + character certificate | Identity document photos (`delivery_partner_documents`, images only, admin-only view) | New `delivery_partner_background_docs`: PDF/JPG/PNG checked from the bytes, max size in rule `riderVerification.maxDocumentBytes`, encrypted in the database (no public bucket), admin states Uploaded → Under review → Approved / Rejected with reason, audited file opening |
| 4 | Location at registration | Optional map pin (`MapPicker`) on the form | Device location (browser / phone) requested at sign-up; registration refused without it, with a clear message; saved with the time |
| 5 | Offline / Active / Ready | Boolean `is_online`; go online only when APPROVED; dispatch takes approved + online riders | `availability` OFFLINE / ACTIVE / READY; only READY gets new offers; Active/Ready blocked until PAN + Aadhaar Verified and police verification (+ character certificate) Approved, unless an admin overrides per partner |
| 6 | Zoning 3–5 km on live location | Rider-to-shop distance ≤ the rider's own radius, from the live location; no rider-to-customer check; no platform radius; nothing re-checked on a location update | Rule `riderZoning` (default 5 km, min 3, max 5): live location within radius of pickup **and** delivery; stale location (> 15 min) not used; open offers re-checked on every location update and withdrawn when out of range |
| 7 | Shop owner: authorised / blocked societies | Society-managed rider list (`society_riders`, ACTIVE/REVOKED); no block; shop owners see no rider list | Admin authorise / block per society (`society_partner_access`); shop page **Delivery partners** with counts of authorised and blocked societies and the list of each on tap |
| 8 | Hide identity for blocked societies | Shop sees the rider's name only in notification text | Server-side: shop order data and shop notifications never carry the name, photo or mobile of a partner blocked in the order's society — "Partner pending assignment"; blocked partners are also kept off that society's orders |
| 9 | Picked up | `markPickedUp` (pickup code / QR), `pickedUpAt`, ACCEPTED → PICKED_UP, shop + customer notified (`order.picked_up`) | Optional photo at pickup (`delivery_proofs.kind = PICKUP`) |
| 10 | Delivered | `markDelivered`: OTP always, photo proof by rule `deliveryProof.photoRequired`; PICKED_UP → DELIVERED | OTP made configurable (`deliveryOtp.required`) |
| 11 | Completed + notify | DELIVERED is final; delivered notices in-app/email; push behind rule `push`; SMS opt-in only | `orders.completed_at` set when delivery is confirmed (status stays DELIVERED — 40 files key on it); `order.completed` event: push + SMS + in-app to the customer and the shop (rule `orderCompletion`); "Completed" shown on both order lists |

Mobile: one Expo app (`mobile/`) showing the website in a WebView, for every
role. New and changed screens are website pages, so both apps get them without a
store update; the native side needs only the version, permission wording and
release notes.
