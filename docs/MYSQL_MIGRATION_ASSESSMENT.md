# Postgres → MySQL: what this actually costs

**Status: assessed, not started. Nothing in this repo has been converted.**

The rest of the bkesari stack is MySQL (`portal`, `edu`, `Ladwani`, `agtci`). This
app — "Asmy Milks", the dairy/bakery ordering app behind `asmymilk.bkesari.com` —
is the one outlier still on PostgreSQL. This document measures what moving it
would take, because the measurement changes the answer.

Every number below was counted from this tree at the commit this document was
added on. Reproduce any of them with the command given.

Baseline: `npm run typecheck` → **0 errors**. The app is healthy on Postgres
today, which is the thing a migration risks.

---

## 1. The headline

A MySQL port here is **not** a schema port. The schema is the small half.

| Surface | Size | Mechanical? |
|---|---|---|
| `src/server/db/schema.ts` | 4,270 lines — 94 tables, 67 enums | Mostly yes |
| `src/server/pmd/**` — a second data layer in raw Postgres SQL | 44 files, 10,317 lines | **No — rewrite** |
| `.returning()` call sites | **180**, across 46 files | **No — control-flow change** |
| `onConflictDoUpdate` / `onConflictDoNothing` | 18 / 18 | Partly |
| SQL casts (`::`) inside `sql` templates | 38 | Mostly yes |
| Postgres full-text search (`to_tsvector`/`to_tsquery`/`ts_rank`) | product search | **No — redesign** |
| `generate_series`, `nextval` | 2 + sequence use | **No — no MySQL equivalent** |
| Existing Drizzle migrations (Postgres SQL) | 37 files | Regenerate from scratch |

Roughly **15,000 lines of database-coupled code**, of which the genuinely hard
parts are concentrated in order, wallet and product-matching paths.

## 2. The three things that make this expensive

### 2.1 MySQL has no `RETURNING` — 180 call sites

```bash
grep -rn '\.returning(' src/ | wc -l     # 180
grep -rln '\.returning(' src/ | wc -l    # 46 files
```

`drizzle-orm/mysql-core` has no `.returning()`, because MySQL has no `RETURNING`.
Each site becomes insert-then-select:

```ts
// today (Postgres)
const [row] = await db.insert(orders).values(v).returning();

// MySQL
const res = await db.insert(orders).values(v);          // no row comes back
const [row] = await db.select().from(orders)
  .where(eq(orders.id, v.id));                          // a second round trip
```

Two things make this more than a find-and-replace:

1. **It must be inside a transaction**, or a concurrent writer can change the row
   between the insert and the select. Not every current call site is in one.
2. **Auto-generated keys.** Where the id is generated by the database rather than
   the app, the select needs `insertId` — which MySQL only reports for
   `AUTO_INCREMENT`, not for a UUID default. This is the main reason the house
   convention (see `agtci`) generates UUIDs in the application
   (`$defaultFn(() => crypto.randomUUID())`) rather than in the database: the app
   knows the id before it inserts, so it can select the row back. Adopting that
   convention here is a prerequisite, not a detail.

The highest-risk files are the ones touching money. `src/server/db/schema.ts`
states the invariant:

> Money is ALWAYS integer paise (bigint). ₹70.00 → 7000. Never a float.
> Financial rows (wallet_transactions, order_items) are immutable once written.

`finance.ts` (10 sites), `subscriptions.ts` (10), `delivery-assignment.ts` (14).
A `.returning()` rewrite that drops a transaction boundary in a wallet path is a
silent money bug, not a compile error — which is exactly why this should not be
done in a hurry.

### 2.2 The PMD layer is Postgres-native by design

```bash
find src/server/pmd -name '*.ts' | wc -l                       # 44
find src/server/pmd -name '*.ts' -exec cat {} + | wc -l        # 10,317
```

`src/server/pmd/db.ts` says what it is:

> The pipeline is set-based and batch-oriented - upserts, ON CONFLICT, trigram
> retrieval - which is what SQL is for, so it talks to postgres.js directly
> rather than through an ORM row-at-a-time.

It is wired to Postgres at the type level — it pins Postgres type OIDs
(`INT8 = 20`, `NUMERIC = 1700`, `DATE = 1082`) to control parsing — and uses, in
plain SQL:

| Construct | MySQL position |
|---|---|
| `pmd.` schema namespace (`pmd.brand_alias`, `pmd.product_seq`) | MySQL has no schema-within-database; becomes a table-name prefix or a second database |
| `ts_rank` / `to_tsvector` / `to_tsquery` | MySQL `FULLTEXT` + `MATCH … AGAINST`: different ranking, different stopword and minimum-token behaviour. Search result ordering **will** change. |
| `nextval('pmd.product_seq')` | No sequences. `AUTO_INCREMENT`, which cannot be read before insert in batch |
| `generate_series(1, n)` | No equivalent. Recursive CTE (MySQL 8+) or a numbers table |
| `ARRAY(SELECT …)` aggregates | `JSON_ARRAYAGG`, returning JSON rather than a native array |
| `ILIKE` | `LIKE` (MySQL's default collation is already case-insensitive) |

This part is a rewrite with behaviour changes that need product sign-off, not a
translation.

### 2.3 Schema details that bite

Mostly mechanical, but none of these are no-ops. The same issues were just solved
for ATIP in `db/mysql.py`, and that experience transfers directly:

| Postgres | MySQL | Note |
|---|---|---|
| `uuid()` × 311 | `varchar(36)` | No native UUID type. App-generated, per §2.1 |
| `timestamp({ withTimezone: true })` × 215 | `datetime` + UTC connection | MySQL has no timezone-aware type. `TIMESTAMP` would also impose a **2038 limit** — wrong for scheduled deliveries and subscription dates, so `datetime` with the connection pinned to UTC (`timezone: 'Z'`, as `portal/db.js` already does) |
| `pgEnum()` × 67, exported and reused across tables | `mysqlEnum()` is per-column | The 67 shared enum objects become exported value tuples, used at each column. `userRoleEnum` alone is referenced as a column type **and** as a primary key in `role_permissions` |
| `text()` × 345 with 209 indexes | `varchar(n)` where indexed | **MySQL cannot index `TEXT` without a prefix length.** Every indexed text column needs a chosen length; `varchar(191)` keeps a 4-column composite key inside InnoDB's 3072-byte limit at utf8mb4 |
| `jsonb` × 24 | `json` | MySQL JSON has no `jsonb` operator set; the 14 `jsonb_*` calls need rewriting |
| `bytea` (`customType`) | `blob` | One definition, `schema.ts:2084` |
| `check()` × 56 | `check()` | Supported in MySQL 8.0.16+; **silently ignored by MariaDB < 10.2 and by MySQL 5.7**. Confirm the host's engine and version first |
| `bigint({ mode: "number" })` × 86 | same | Fine |

## 3. What I recommend

**Leave this app on PostgreSQL for now, and move it last — if at all.**

Reasons, in order of weight:

1. **Nothing is blocked by it.** It is deployed at `asmymilk.bkesari.com`, its own
   subdomain, with its own database. The portal, `edu`, `Ladwani` and `agtci` are
   already MySQL and do not share a database with it. "One engine across the
   stack" is a tidiness goal, not a dependency — and the three-tier
   dev → test → production rollout in `bkesari-platform/DEPLOY.md` works without it.
2. **The risk is concentrated in money.** 34 of the 180 `.returning()` sites are
   in `finance.ts`, `subscriptions.ts` and `delivery-assignment.ts`. The failure
   mode is a wrong balance, not a stack trace.
3. **Search behaviour changes.** Moving off `ts_rank` changes product search
   ordering. That is a product decision with a visible user effect, and it should
   not arrive as a side effect of a database migration.
4. **Managed Postgres is cheap and already configured.** `src/server/db/index.ts`
   handles Neon/Supabase/RDS TLS and a configurable pool ceiling. Hosting the
   database off Hostinger costs less than this migration.

### If it does go ahead, stage it

Each stage ends green — `npm run typecheck && npm run test && npm run build` — and
is independently revertable.

| Stage | Work | Rough size |
|---|---|---|
| 0 | Decide: MySQL 8 or MariaDB, and which version (`check()` support, §2.3). Stand up an empty database per tier | hours |
| 1 | **DONE** (`b26c977`) Adopt app-generated UUIDs (`$defaultFn`) on Postgres, unchanged behaviour. Unblocks §2.1 | ~0 — one 86-line helper; no migration, 814/814 tests |
| 2 | **Largely dissolved** by the self-transacting helper above. Measured on this tree: 180 sites split 111 update / 53 insert / 16 upsert; 64 already inside a transaction; of the 116 that were not, stage 1 makes the 29 plain inserts safe, leaving 87 — and of those, 4 are false positives already running on a passed `tx` and 7 delegate to a caller-supplied `client`. So ~75 sites, none of which need editing if the helper opens its own transaction | hours, not days |
| 3 | Port `schema.ts` to `mysql-core`; regenerate all 37 migrations. Index-aware `text`→`varchar`, per §2.3 | 3–5 days |
| 4 | Swap the driver (`postgres-js` → `mysql2`) and convert the 180 `.returning()` sites, now that stage 2 made them safe | 5–8 days |
| 5 | Rewrite the PMD layer, including the FULLTEXT search redesign | 2–3 weeks |
| 6 | Dual-run both engines against production traffic, diff results, then cut over | 1 week |

Stages 1 and 2 are worth doing **regardless** of whether the migration ever
happens: they make the money paths more robust on Postgres too.

### What is already done elsewhere

**The `bkesari` repo has already been ported** — `claude/amazing-cannon-5n3fro`,
open as PR #9 there, "Port Milk & Dairy from PostgreSQL to MySQL for Hostinger",
reporting 275/275 tests passing against MariaDB 10.11 and MySQL 8.0.46 with a
52-table schema migrating cleanly.

That is the same application, and it does **not** mean this port is easy. It means
the port is easy *where the two hard parts are absent*, and `bkesari` is the
smaller, older variant where they are:

| | `bkesari` (ported) | here |
|---|---|---|
| `schema.ts` | 2,316 lines, 52 tables | **4,270 lines, 94 tables** |
| `.returning()` sites | **0** | **180** |
| `src/server/pmd/**` | **does not exist** | **44 files, 10,317 lines** |

So its success is evidence *for* §2, not against it: the obstacles that make this
port expensive are the ones that repo never had.

**What is directly reusable, though, is the hardest single piece.** That branch adds
`src/server/db/returning.ts`, which reproduces `RETURNING` on MySQL and already
solves the correctness trap §2.1 warns about — it distinguishes two cases that a
naive insert-then-select conflates:

- `updateReturning` — for an update whose `WHERE` does not test a column the update
  changes. Re-reading the same `WHERE` afterwards is exact.
- `updateReturningIfChanged` — for a **compare-and-swap** guard
  (`SET status='SUCCESS' WHERE status='CREATED'`), where re-reading the `WHERE`
  afterwards matches nothing, and an empty result is exactly how callers detect a
  lost race. It judges by the affected-row count instead.
- `insertReturning` — generates the id in the application (`crypto.randomUUID()`)
  so the inserted rows can be read back, since MySQL's `LAST_INSERT_ID()` only
  covers `AUTO_INCREMENT`. That is **stage 1 of the plan above, already written**.
- `upsertReturning` — keeps Postgres's explicit conflict target, not because MySQL
  needs it (`ON DUPLICATE KEY UPDATE` picks the key itself) but because it names
  the columns to read the row back by.

This changes the estimate for stage 4 from "design and apply 180 times" to "port a
reviewed helper and apply it 180 times", and it removes the design risk from the
money paths. It does **not** touch §2.2: `bkesari` has no PMD layer, so nothing
there addresses the `ts_rank` search, the `pmd.` namespace, the sequences or
`generate_series`. That remains the largest single piece of work.

### A race in that helper — do not copy it as-is

`bkesari`'s helpers take the executor as their first argument, and **58 of its 81
call sites pass `db`, not a transaction** (22 pass `tx`, 1 passes a `client`):

```ts
const [record] = await updateReturning(db, users, { role: "ADMIN" }, eq(users.id, id));
```

`updateReturning` runs three statements — `select` the matching ids, `update`
them, `select` the rows back. With `db` they are three separate transactions, so
another writer can change the row between the first and the third and the
returned rows need not reflect what this update did. PostgreSQL's
`update().returning()` was a single statement and therefore exact. The helper's
own docstring is careful about *which* `WHERE` can be re-read safely, but
atomicity is left to the caller and most callers do not provide it.

So the helper is the right shape and the wrong default. Here it should make
itself atomic instead of hoping the caller does:

```ts
/** Run `fn` inside a transaction unless the caller already gave us one. */
async function atomically<T>(exec: DbClient, fn: (tx: DbClient) => Promise<T>) {
  // `exec === db` means no transaction was passed. The read-modify-read below is
  // only equivalent to RETURNING when it is atomic, so open one. When a tx WAS
  // passed we must use it rather than nest.
  return exec === db ? db.transaction((tx) => fn(tx)) : fn(exec);
}
```

**This is what makes stage 2 cheap.** Wrapping call sites by hand was the
expensive half of the estimate; with a self-transacting helper the call sites do
not change at all, and atomicity cannot be forgotten at a call site because it is
no longer a call-site decision.

Other precedents:

- `agtci` is the house style guide — commit `9db30ad`, "Convert schema/driver from
  Postgres to MySQL (Hostinger-hosted)": `mysqlTable`, `mysqlEnum`, `json`, and
  `varchar(36)` ids via `$defaultFn(crypto.randomUUID)`. 8 tables, so style only.
- ATIP's `db/mysql.py` solves the same dialect problems on the Python side, with
  the `TEXT`-cannot-be-indexed and reserved-word rules worked out and verified
  against a real server (`tests/test_mysql_backend.py`).

# Stages 3 + 4: the execution plan, with the decisions resolved

Stages 3 and 4 have to land as one commit: porting `schema.ts` to `mysql-core`
breaks every service file until the call sites follow, so there is no green state
in between. This section records what was measured and decided before starting,
so the diff can be reviewed against intent.

## The decision that unblocks it: PMD stays on PostgreSQL

`src/server/pmd/**` is 44 files and 10,317 lines of raw Postgres SQL (§2.2) and is
the largest remaining piece. It does **not** have to move at the same time,
because it is separated at the data layer:

- its SQL touches **no** app table — every `FROM`/`JOIN`/`INSERT` is `pmd.*`
- it owns its own client (`src/server/pmd/db.ts`, `createSql`), independent of the
  Drizzle client
- the only coupling is **code**: 16 app files import PMD functions, which use
  PMD's own connection and are unaffected by the Drizzle driver swap

So the app's Drizzle layer moves to MySQL while PMD keeps a PostgreSQL
connection. **This means two databases in production** — MySQL for the app,
PostgreSQL for the product-master pipeline. On Hostinger that needs an external
Postgres for PMD (Neon or similar), which `src/server/db/index.ts` already
handles TLS for. It is reversible: porting PMD later is stage 5, unchanged.

Flagging it plainly because it changes production topology and hosting, not just
code.

## Type mapping, as measured on this schema

| Postgres | count | MySQL | why |
|---|---|---|---|
| `pgTable` | 94 | `mysqlTable` | |
| `pgEnum` (shared objects) | 67 | shim, below | |
| `uuid` | 226 | `varchar(36)` | no native UUID |
| `timestamp({withTimezone:true})` | 215 | `datetime({mode:"date"})` | MySQL has no tz-aware type. `TIMESTAMP` would add a **2038 limit**, wrong for scheduled deliveries and subscriptions. UTC by convention, connection pinned to `Z` |
| `text` **that is indexed** | 54 | `varchar(255)` | MySQL cannot index `TEXT` without a prefix length |
| `text` (not indexed) | 253 | `text` | |
| `jsonb` | 24 | `json` | the 14 `jsonb_*` calls need rewriting |
| `integer` | 82 | `int` | |
| `bigint({mode:"number"})` | 86 | unchanged | mysql-core takes the same option |
| `boolean`, `date` | 37, 25 | unchanged | native |
| `check` | 56 | `check` | MySQL **8.0.16+** enforces these; confirm the host's version |
| `customType` `bytea` | 1 | `blob` | |

**`varchar(255)`, not the usual 191.** Measured: with 255 the widest index in the
schema is **2,044 bytes**, well inside InnoDB's 3,072-byte limit, and **zero**
indexes exceed it. 191 would have truncated `users.email` and `grievances.email`,
which RFC 5321 allows up to 254 characters.

## The enum shim: 67 declarations change, 112 usages do not

`pgEnum` returns a reusable object; `mysqlEnum(name, values)` is per-column. But
`.enumValues` is used **62 times** — in `users.ts`, `roles.ts`,
`ops-exceptions.ts` and ~50 exported type aliases like
`export type GstStatus = (typeof gstStatusEnum.enumValues)[number]`. It is public
API of the schema module.

So the shim keeps it, and nothing outside the declarations changes:

```ts
function mysqlEnumType<const T extends readonly [string, ...string[]]>(values: T) {
  return Object.assign((name: string) => mysqlEnum(name, values), { enumValues: values });
}
```

Verified against all three usage shapes: as a column factory, as
`new Set(x.enumValues)`, and as `(typeof x.enumValues)[number]`.

## Two constructs with no MySQL equivalent

**PostgreSQL arrays — 2 columns.** `delivery_orders.rejected_partner_ids` and
`return_pickups.rejected_partner_ids`, both `uuid[]`, tracking riders who declined
so they are never re-offered. Becoming `json`, with four operator rewrites across
~8 call sites:

| Postgres | MySQL |
|---|---|
| `array_append(c, v)` | `JSON_ARRAY_APPEND(c, '$', v)` |
| `x = any(c)` | `JSON_CONTAINS(c, JSON_QUOTE(x), '$')` |
| `cardinality(c)` | `JSON_LENGTH(c)` |
| `'{}'::uuid[]` / `[]` | `JSON_ARRAY()` |

**Three sequences producing user-visible identifiers.** MySQL has no sequences:

| Column | Format | Where it surfaces |
|---|---|---|
| `shops.registration_number` | `BKS-000001` | admin shop search |
| `products.code` | `P00001` | Excel import/export |
| `grievances.ticket_number` | `GRV-000123` | the `/grievance/{ticket}` URL a complainant quotes back |

These cannot stay column defaults — MySQL cannot call a generator in a `DEFAULT`.
They become a `counters` table incremented with MySQL's atomic idiom, formatted in
the application:

```sql
UPDATE counters SET n = LAST_INSERT_ID(n + 1) WHERE name = ?;
SELECT LAST_INSERT_ID();   -- the new value, per-connection, race-free
```

This is a real behaviour change: any insert that previously relied on the column
default must now supply the value, so every insert site for those three tables
needs checking. They are business identifiers, so they must stay unique and
monotonic — the idiom above is atomic, but it is not gap-free across rolled-back
transactions, which is the same guarantee `nextval` gave.
