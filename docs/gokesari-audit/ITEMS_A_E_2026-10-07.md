## 1. What changed, per item

### A — Cancellation before packing refunds everything (D10 / D6)

* **Finding:** every cancellation path that can run before an order is packed
  already refunds the **full amount, delivery fee included** — the shop or
  operations cancelling at CONFIRMED / ACCEPTED / PREPARING, the acceptance
  timeout, a suspension's CANCEL_REFUND, "all items unavailable", and the
  customer at CONFIRMED. No money logic was changed; new tests pin each path.
* **New rule `cancellation.customerMayCancelUntil`** (`CONFIRMED` default = D10
  as today | `PREPARING`). With `PREPARING` a customer may also cancel an
  accepted or picking order — same full refund — and the shop is notified.
  Packed and later stages are unchanged.
* Files: `src/server/config/rules.ts`, `src/server/services/orders.ts`,
  `tests/integration/cancellation-before-packing.test.ts`.

**Cancellation after packing — unchanged (for your decision):**

| Order status | Customer cancels own order | Shop / operations cancel |
|---|---|---|
| READY (packed), ASSIGNED (rider accepted) | Refused: "already being prepared, contact the shop" | Allowed, **full refund incl. delivery fee**; an assigned rider is released, no rider earning |
| PICKED_UP, OUT_FOR_DELIVERY | Allowed, **goods only refunded; delivery fee kept** and journaled as platform DELIVERY_FEE revenue; the rider is still paid (`riderEarnings.cancelledAfterPickupPayoutPercent`, default 100 %) | Allowed, **full refund incl. delivery fee**; the rider is still paid (platform cost) |
| FAILED, RETURNED, DISPUTED | Refused: "contact support" | Allowed, full refund |

Every cancel restocks (except lines the shop removed); a partial refund is
never repeated; no invoice exists before delivery. The code comment still
marks the ACCEPTED/ASSIGNED and PICKED_UP extensions of D10 as "pending your
confirmation".

## 5. Open points

### SM-006 — how disputes relate to the issue state machine (unchanged)

* **Required (SM-006):** OPEN → TRIAGED → INVESTIGATING → RESOLUTION_PROPOSED →
  RESOLVED → CLOSED, exception ESCALATED, linked to order/payment.
* **Today there are two records.** "Report an issue" on an order creates a
  **grievance** (statutory redressal record, Grievance Officer): OPEN /
  IN_PROGRESS / RESOLVED / CLOSED, linked to the order, any order status,
  categories ORDER / PRODUCT / PAYMENT. A **dispute case** (GS-058) is opened
  by the customer or operations **only on a delivered order**, may link the
  grievance that started it, and has OPEN → TRIAGED → INVESTIGATING →
  RESOLUTION_PROPOSED → RESOLVED, ESCALATED from any live state (L1 operations
  → L2 admin; auto-escalation after 48 h or above ₹2,000 via the hourly
  dispute-escalation cron), plus REJECTED / WITHDRAWN. Resolving with a refund
  goes through the finance refund. A dispute never changes the order's status;
  the order's DISPUTED status is a separate operations action.
* **(a) Accept the dispute lifecycle as SM-006:** no code. Every SM-006 state
  exists except an explicit CLOSED (RESOLVED / REJECTED / WITHDRAWN are the
  terminal states). Gaps that remain: problems before delivery and
  payment-only problems are handled as grievances (four states, no triage /
  escalation); two records per complaint stay.
* **(b) Add the four states to grievances:** add TRIAGED, INVESTIGATING,
  RESOLUTION_PROPOSED, ESCALATED to `grievance_status` (a Postgres enum —
  values can be added but not removed, so the rollback is "stop using them"),
  a transition table, Grievance manager buttons, dashboard counts and the
  overdue rule, notifications, tests; map IN_PROGRESS to the new states for
  existing rows. Result: two parallel machines with the same states (grievance
  and dispute) that operations would have to keep in step, and the statutory
  record gets workflow states the rules do not require.
* (c, alternative) Auto-open a dispute from "Report an issue" when the order is
  delivered — one workflow, grievance stays the statutory record.

## 6. Decision log

- A5. Invoices are issued only at DELIVERED, so no credit-note handling needed for pre-packing cancels.

### Deploy tooling (added on request, 8 Oct)
- M-1. Automatic migration runs inside `npm run build` (before `next build`), not as a GitHub Actions job: a separate job races Hostinger's own deploy, so the new code could go live before the migration ends, and a failed migration would not stop the deploy. In the build, a failed migration fails the build.
- M-2. Opt-in per environment with `MIGRATE_ON_BUILD=true` (accepts `true`/`1`); unset = previous build exactly (logs "skipped"). Production keeps migrating by hand until the owner decides otherwise.
- M-3. Plain Node script using only runtime dependencies (`drizzle-orm`, `postgres`), not `tsx`, so it works even if the host builds without devDependencies. Loads `.env*` files through `@next/env` — the loader `next build` itself uses — so it sees the same `DATABASE_URL` as the build however the host provides variables.
- M-4. Logs database name and host only, never the connection string. No advisory lock: drizzle already applies all pending migrations in one transaction, so a second concurrent build fails on the duplicate DDL rather than half-applying, and a session lock could leak through a pooled (PgBouncer) Neon connection.
- M-5. No backup is taken by the script; the runbook keeps the backup step before each merge that carries migrations.
- M-6. 8 Oct: the owner asked for migrations on test to be done from the session and test deploys to go ahead without waiting ("not live, just testing"). Test database migrated as recorded in §3; the PR goes into `staging` once CI and the full local pass are green on its head. Production stays manual and needs the owner's go-ahead per release — the earlier "never production" instruction stands.
- M-7. The session's container cannot reach PostgreSQL on port 5432 (HTTPS egress only), so the migration used Neon's SQL-over-HTTPS transaction with drizzle's `readMigrationFiles` (same statements, hashes, `created_at`), guarded to the test host and to exactly 0056+0057 pending. `MIGRATE_ON_BUILD=true` on test.gokesari.com is the durable way to have every merge to `staging` migrate without anyone holding the password.
