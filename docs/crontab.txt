# GoKesari — the complete cron schedule (owner, 19 Oct 2026), the same on BOTH
# sites. Since 17-Nov-2026 it runs on our own server (gk-db-1) as systemd timers,
# not in hPanel: hPanel has no GoKesari cron lines any more (test.gokesari.com's
# were removed 08.21 IST, gokesari.com's 08.36 IST). Kit:
# scripts/vps-app/README.md, "Cron". Times below are UTC (IST = UTC + 5:30), as
# the lines were written; the server's timers run the same moments on its IST
# clock.
#
# Everything a customer, shop or rider does is handled by its event at once.
# These three jobs cover only what no event can start: a deadline passing, a
# retry after a failed send, a gateway reply that never came, a timed send, the
# 05:00 subscription orders and the payouts (shops weekly, riders and dealers
# monthly). What each job runs, and
# how often: docs/cron-schedule.md.
#
# Each run POSTs /api/cron/<job> with the CRON_SECRET bearer token. Every job is
# idempotent: a late, overlapping or repeated run is harmless.

# Both sites — gokesari.com and test.gokesari.com:
* * * * *    every-minute   # timeouts, retries, queued sends (each at its own cadence)
17 * * * *   hourly         # risk scan, dispute + help-desk deadlines, refund / payout retries, expired codes
30 23 * * *  daily          # 05:00 IST: subscription orders, document upkeep, GST reminders, Saturday payout, Monday finance week

# On the server (gk-site cron <site> on|off|status):
#
# | Job          | Timer (server clock, IST)       | curl --max-time |
# |--------------|---------------------------------|-----------------|
# | every-minute | *-*-* *:*:00                    | 55              |
# | hourly       | *-*-* *:47:00 Asia/Kolkata      | 300             |
# | daily        | *-*-* 05:00:00 Asia/Kolkata     | 300             |
#
# Units: gk-cron@gokesari-prod-<job>.timer and gk-cron@gokesari-staging-<job>.timer.
# Each run is `gk-cron-call <site> <job> <max-time> <domain>`, as the site's
# user: systemd loads the site's env file (so CRON_SECRET never appears in a
# command line), `flock -n` skips a run while the previous one is still going,
# and curl calls the serving colour on 127.0.0.1 with the site's Host header.
# The app also runs only one copy of each entry point at a time
# (src/server/cron/single-run.ts) and answers an overlapping call with
# {"skipped":true,"reason":"ALREADY_RUNNING"}.
#
# The every-minute job must keep running at whole minutes: dueEveryMinute
# (src/server/cron/schedule.ts) runs the 5-, 10- and 15-minute jobs (payments
# reconcile, operator onboarding fees, document e-mails, bill captures, push
# receipts) only when the UTC minute is a multiple of their interval. IST's
# +5:30 offset keeps those multiples.
#
# Staging history: from 16-Nov-2026 test.gokesari.com's every-minute line ran
# only every 6 hours (`0 */6 * * *`) to cut Neon compute. With the database on
# our own server it runs every minute again (owner, decision D7, 17-Nov-2026).
#
# Before 17-Nov-2026 these were hPanel cron lines (Advanced → Cron Jobs →
# Custom), one set per site, of the form:
# * * * * *   flock -n $HOME/gokesari-cron/<site>/every-minute.lock curl -fsS --max-time 55 -o /dev/null -X POST https://<host>/api/cron/every-minute -H "Authorization: Bearer $(cat $HOME/gokesari-cron/<site>/secret)"
# 17 * * * *  flock -n $HOME/gokesari-cron/<site>/hourly.lock curl -fsS --max-time 300 -o /dev/null -X POST https://<host>/api/cron/hourly -H "Authorization: Bearer $(cat $HOME/gokesari-cron/<site>/secret)"
# 30 23 * * * flock -n $HOME/gokesari-cron/<site>/daily.lock curl -fsS --max-time 300 -o /dev/null -X POST https://<host>/api/cron/daily -H "Authorization: Bearer $(cat $HOME/gokesari-cron/<site>/secret)"
# Rolling back to Hostinger (until 1-Dec-2026): `gk-site cron <site> off` and
# re-create that site's three lines in hPanel in the same minute, so each job
# runs in one place only.
#
# The old per-job endpoints (/api/cron/shop-acceptance, /timeout-sweep,
# /daily-orders, …) still answer, for a manual run or a backfill
# (docs/event-driven-2026-10/ROLLBACK.md). Don't schedule them next to the three
# entry points above: each job would then run twice.
