## 1. Conflicts found in the current code (need your decision)

1. **No shop staff role exists.** `shops.owner_id` is the only link; "staff" in
   the code means operators/admins. → Add a `shop_staff` table (§2 M1).
2. **No shop-level MRP exists.** MRP is master-only and the shop's own *selling
   price* is per shop. I read your rule "an MRP changed by a shop owner applies
   only to that shop" as that per-shop price, which stays as is. A price pulled
   from shop software goes into that shop's listing only.
3. ~~**No shop wallet exists.**~~ *Superseded: PR #91 added one; it is reused.* Customers have wallets; shops are paid through
   settlements/ledger. → Add a `shop_wallets` account (zero balance) at
   approval; nothing flows into it yet. Tell me what it should hold.
4. **No SMS or WhatsApp provider exists.** Every OTP and notice goes by email.
   → Add provider slots (mock on test; one real adapter each once you pick).
5. **Accounts need an email** (`users.email` NOT NULL). → Phone-only owners get
   a non-deliverable placeholder address (`m91XXXXXXXXXX@phone.invalid`) flagged
   `email_placeholder = true`, never emailed; they add a real email in the
   profile step.
6. **New shops need address, city, pincode, owner name, shop type** (NOT NULL).
   Registration collects none of these. → Stored empty, shop type
   `GENERAL_TRADING`, filled in "complete your profile". Consequence: the shop
   is live and **searchable by name** at once, but appears in **nearby /
   delivery-area results only after an address is saved**.
7. **Auto-approval skips document checks.** Today a shop needs PAN, GSTIN or
   declaration, Shop Act and FSSAI (food shops) before approval. The new flow
   approves on referral + payment alone, as you asked. The existing
   document-based auto-approval and the manual flow are not changed.
8. **The current invoice number is 25 characters** (`BKS-000123/2026-27/000001`).
   GST Rule 46 and the e-invoice schema allow at most 16. → A switch
   `documentNumbering = LEGACY | GST16` (default LEGACY, no change). GST16
   gives `GK2627-000001` per shop per FY. Must be GST16 before e-invoicing.
9. **Refunds after delivery are amount-only, not per line.** → A credit note
   for a partial refund spreads the amount across invoice lines in proportion.

## 2. Module 1 — shop product photos and descriptions

### Behaviour
- Owner or staff opens a product in their shop → mobile screen: **Take photo**
  (camera) / **Choose from gallery**, up to 5 photos, drag to reorder (touch),
  first = main, short description (≤ 160 chars), long description (≤ 4,000).
- Server, per photo: ≤ 5 MB; real type from magic bytes (JPG/PNG/WebP only)
  and confirmed by the decoder; decompression-bomb limit; EXIF orientation
  applied then **all metadata stripped**; resized to thumbnail 200 px, medium
  600 px, large 1,200 px (longest side); WebP; original discarded.
- Stored outside the web root under random names: Postgres (today's store) or
  a directory set by `MEDIA_DIR` (random 32-hex names, sharded, mode 0700,
  never under `public/`). Served only through `/api/images/{id}?size=`.
- Customers: listing shows the shop's main photo and short description;
  product page shows the shop's gallery and long description. Anything the
  shop hasn't set falls back to the master photo/description.
- Bulk: ZIP of photos named `<SKU or barcode>.jpg` or `<SKU>_2.jpg` (position
  1–5) plus CSV `sku_or_barcode, short_description, long_description`. Match
  order: SKU (`products.code`) → GTIN → barcode, only among that shop's
  listings. Preview of matched / unmatched / invalid rows → Apply. Images are
  processed right after Apply with a live progress bar; an interrupted import
  can be resumed (no cron).
- Who may edit: shop owner, the shop's active staff, and operators/admins
  (support, logged). Every change is audited with before/after values; a
  per-product history list shows who changed what and when.
- Image moderation (existing rule, off by default) still applies.

## 3. Module 2 — accounting / inventory integration and GST

### 3.1 Shape
```
              PULL items · stock · price/MRP · HSN · tax rate
shop software ───────────────────────────────▶ adapter ─▶ canonical ─▶ mapping ─▶ shop_products
              ◀─────────────────────────────── adapter ◀─ canonical ◀─ integration_jobs (outbox)
              PUSH sales invoice · credit note · stock reduction       ▲ enqueued in the same
                                                                       │ transaction as DELIVERED /
                                                                       │ refund, run just after commit
```
- **Canonical format** (`src/server/integrations/canonical.ts`, zod):
  `Item`, `StockLevel`, `Price`, `Customer`, `SalesInvoice`, `CreditNote`,
  `StockAdjustment`, all carrying GSTIN, HSN/SAC, rate, CGST/SGST/IGST/cess,
  place of supply, supply type, UQC, round-off.
- **Adapter interface**: `capabilities`, `testConnection`, `pullItems`,
  `pushInvoice`, `pushCreditNote`, `pushStockAdjustment`; file adapters also
  `parseImport(file, mapping)` / `exportFile(kind, records)`. One registry,
  one active connection per shop, chosen in **Shop settings → Integrations**.

### 3.2 Adapters
| Software | Transport | Pull | Push | Idempotency key in the target |
|---|---|---|---|---|
| **TallyPrime** | Windows connector ↔ `localhost:9000` XML | Stock items (name, alias/part no., unit, closing stock, rate, MRP, HSN, GST rate), only items changed since the last `ALTERID` | Sales voucher (Invoice view, inventory + CGST/SGST/IGST ledgers), Credit Note voucher; stock falls with the voucher | `VOUCHERNUMBER` = our number + `REMOTEID`, checked before create |
| **Odoo 19+** | JSON-2 `POST /json/2/<model>/<method>`, bearer API key, `X-Odoo-Database` | `product.product`, `stock.quant` | `account.move` (out_invoice / out_refund) + `stock.quant` adjustment (an invoice does not move stock in Odoo) | `ref` searched before create |
| **Zoho Books (India DC)** | REST, OAuth 2.0 via `accounts.zoho.in`, `www.zohoapis.in` | `/items` | `/invoices`, `/creditnotes`; stock falls with inventory-tracked items | `reference_number` searched before create |
| **myBillBook, Vyapar** | Excel/CSV | Upload their item export → column-mapping screen | Download invoices / credit notes / stock-out sheet in their import layout | Exported rows marked; re-export never duplicates |
| **Generic CSV/Excel** | Excel/CSV | Same, no preset | Same | Same |

Layouts for myBillBook/Vyapar are presets on the generic mapper. They will be
marked "unconfirmed" until I see a real export file from each app. The adapter
interface keeps an API slot for both.

**Tally connector** (`connector/tally/`): small Windows program (Node, built
into one `.exe` by a GitHub Actions Windows job), installed as a Windows
service.
- Signs in with a shop API token: shown once, stored hashed, revocable.
- Talks only outbound HTTPS to gokesari: long-polls for jobs (the request is
  held about 25 s, so a job is picked up within a second), sends the Tally XML
  to `localhost:9000`, posts the result back.
- Checks Tally locally every 2 minutes for changed items (`ALTERID`) and
  uploads only the changes.
- Never opens a port; Tally's port is never exposed. The XML is built and
  parsed on the server, so the connector stays a dumb pipe and rarely needs
  updating.

### 3.3 Sync engine
- `integration_jobs` is an outbox: unique `idempotency_key`
  (`invoice:<invoiceId>:<connectionId>`). Enqueuing the same thing twice is a
  no-op, so retries never create a second invoice.
- Claimed with `FOR UPDATE SKIP LOCKED` and a lease; a crashed claim is
  re-claimed after the lease.
- Every push is check-then-create in the target. A retry after a lost
  response finds the document already there and records it, without creating
  a second one.
- Retry with backoff. After N attempts the job is DEAD: the owner is notified
  and it shows on the error screen with a **Retry** button.
- Triggers, all events (no schedule):
  - DELIVERED (order complete on delivery OTP) → invoice issued → push job.
  - Refund after delivery (`refundDeliveredOrder`, including returns) →
    credit note issued → push job.
  - Pull runs on **Sync now**, on connector start and on connector change
    detection, and on Odoo/Zoho webhooks where the shop sets them up.
  - The existing every-minute safety-net sweep also re-runs due API jobs.
- Cancellations before delivery have no invoice, so nothing is pushed. Stock
  given back on cancel stays gokesari-side.
- **Conflict rule:**
  - Pulled stock and price overwrite the shop listing; the software is the
    source of truth.
  - Online stock = software quantity − units in open online orders not yet
    invoiced, so pulling never resells goods already sold online.
  - Orders stay gokesari's.
  - A pulled price above the verified master MRP is **not applied**; it is
    shown as an error, as MRP governance does today.
- **Mapping screen:**
  - Automatic match on barcode/GTIN, then SKU, then name (trigram
    similarity, shown as "suggested").
  - Manual search-and-pick or "ignore" for unmatched items.
  - A matched product the shop doesn't list yet is added to the shop.
- **Sync log and error screen** per shop. Every error code maps to a
  plain-language message and a fix, e.g. "Tally is not open on your shop
  computer — open Tally and keep the GoKesari Connector running".
- **Security:**
  - Credentials are encrypted with AES-256-GCM using a new
    `INTEGRATION_ENCRYPTION_KEY`, with a key version for rotation.
  - Credentials are write-only in the API.
  - Every route checks shop ownership, and a connector token is bound to one
    shop and one connection.

### 3.4 Shop HSN / tax rate
HSN and tax rate pulled from the shop's software are stored on that shop's
listing (`shop_products.hsn_code / gst_rate_bp / cess_bp`). That shop's
invoices use them; the master is untouched. The shop is the supplier and is
responsible for its classification. A mismatch with the master is shown to
admins.

### 3.5 GST through a GSP (provider-agnostic)
`GspProvider` interface: `validateGstin`, `generateIrn`, `cancelIrn`,
`generateEwayBill`, `cancelEwayBill`. Adapters: `mock` (sandbox-shaped, used
by tests and by test.gokesari.com until GSP keys arrive) and one real GSP
once you choose it. Env: `GSP_PROVIDER`, `GSP_ENV=sandbox|production` (same
host-pairing guard as KYC).

- **Phase 1:**
  - GSTIN validation in "complete your profile": legal name, trade name,
    status, state and type, cached in `gstin_lookups`. This also wires the
    existing owner GST form.
  - Invoice PDF gaps closed for Rule 46: state name + code, reverse charge
    "No", UQC, round-off, cess, authorised signatory line, amount in words.
  - `invoicing.enabled` turned on for test.
- **Phase 2:**
  - IRN + signed QR through the GSP, only for shops marked e-invoice
    applicable and only for B2B invoices (buyer GSTIN).
  - E-way bill when the value and state rules from config say so.
  - Both run as jobs after invoice issue, with retry.
- **Phase 3:**
  - Monthly GSTR-1-ready export per shop: JSON in the GST offline-tool shape
    (B2B, B2CL, B2CS, CDNR, CDNUR, HSN summary split B2B/B2C, documents
    issued) and Excel.
  - Download only, for the shop or its CA. Nothing is filed.
- **Config, not code:**
  - `gst_rules` is a dated key/value table, so the rule in force on the
    invoice date applies. Seeded: e-invoice turnover threshold ₹5 crore, IRN

  - All are editable at `/admin/gst-config`.

## 4. Module 3 — shop registration with auto-approval

### Flow (public, mobile-first `/shop/join`)
1. Shop name, mobile, referral code → **code checked before anything else**.
   Not found / inactive / expired / usage limit reached → blocked with a clear
   message, no payment possible.
2. OTP by SMS → verified.
3. Registration saved as **PENDING_PAYMENT**. It holds a slot on the code's
   usage limit for 24 h (rule), with a private retry link `/shop/join/{token}`
   (also sent by SMS).
4. Pay the fee for the code's tier through Cashfree (`reg_…` order,
   `notify_url` = the existing webhook). The browser return only shows status;
   **it never approves.**
5. **Webhook** (`/api/webhooks/cashfree`, existing route, extended):
   1. Verify the signature (existing HMAC).
   2. Payment status SUCCESS, currency INR, and **order and payment amounts
      equal the fee snapshot**. Otherwise no approval: the payment is marked
      MISMATCH and support is alerted.
   3. **One transaction:** lock registration → registration APPROVED → find
      or create the owner's account (mobile verified) + SHOP_OWNER role →
      shop inserted **APPROVED** (classification from rule, default GREEN),
      fee PAID → `shop_payments` receipt (`PAY-…`, method CASHFREE) →
      referral redemption → **shop wallet** → **distributor commission**
      (ACCRUED) → audit → `emitEvent('shop.self_registered')`.
   4. Right after commit: SMS + WhatsApp + email to the owner (welcome,
      login link, receipt link) and an in-app note to support.
6. Failed / dropped payment → stays PENDING_PAYMENT, owner gets the retry
   link. A valid webhook later (even after the 24 h hold) approves at once.
7. **Idempotent webhook:**
   - unique gateway payment id;
   - conditional status update;
   - registration row lock + status check;
   - unique `shop_registrations.shop_id`;
   - unique commission per registration;
   - unique redemption per shop;

## 10. Assumptions
- "Order complete" = DELIVERED by rider OTP **or** the operator's
  confirm-delivery fallback. Both already issue the invoice; both will
  enqueue the push.
- A refund after delivery always produces a credit note; cancellations before
  delivery have no invoice and need none.
- The registration receipt is the existing `PAY-YYYY-NNNNNN` shop payment
  receipt, as a PDF.
- A mobile that already belongs to an account becomes the owner of the new
  shop; the same mobile may own more than one shop, each paying its own fee.
- Owner and staff edits apply at once; image moderation, when switched on,
  still hides new photos until approved.
- GST rates are not seeded. Products without a rate keep today's behaviour
  (rule default, marked "rate assumed" on the invoice).
