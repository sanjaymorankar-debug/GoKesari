## 3. Why step 3 was not switched in this run

1. **It changes production and is not a config-only switch yet.** README §5:
   phase 2 (logical replication from the source into both new databases, so
   they stay current) and phase 3 (moving each service area onto
   `sellerDb()` / `customerDb()`) are separate releases. Most services still
   use the single `db` handle, so `DB_SPLIT_MODE=split` today would point only
   the seller handle at a copy that stops receiving writes the moment it is
   taken — the seller copy would go stale. That is a data-integrity risk on
   gokesari.com, and the brief's rule is to stop at irreversible production
   actions.
2. `DB_SPLIT_MODE` is a Hostinger environment variable (hPanel), which this
   build environment cannot change.

**Status: IN PROGRESS / BLOCKED-OWNER-INPUT** — the owner's go-ahead for the
cut-over window, plus the phase-2 replication set-up on Neon (enable logical
replication on the project).

## 4. Cut-over runbook (for the owner's window)

1. Production database workflow → `migrate` (brings production to 0084).
2. Neon console → production project → create a branch named
   `pre-split-YYYYMMDD` (backup).
3. Database split → production → `migrate`, `replace` = true, confirm
   `SPLIT PRODUCTION`. Must report PASS.
4. Database split → production → `fdw` (cross-database reads), confirm
   `SPLIT PRODUCTION`.
5. Neon: enable logical replication; create the publication/subscriptions
   (README §5 phase 2). Run `verify` daily for 7 days in `shadow`.
6. Hostinger → gokesari.com → environment: `DB_SPLIT_MODE=shadow`,
   `SELLER_DATABASE_URL`, `CUSTOMER_DATABASE_URL`; redeploy; smoke test.
7. Only after phase 3 has moved the service areas (one release per area,
   test.gokesari.com first): `DB_SPLIT_MODE=split`; smoke test.
8. Rollback at any point within 7 days: `DB_SPLIT_MODE=single`, redeploy.
